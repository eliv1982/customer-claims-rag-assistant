# Final acceptance evidence

Current evidence for release `foodflow-10doc-release-v2`: the canonical 10-document corpus, 216 chunks, built into `data/04_index_production`. It is generated by [`scripts/capture_final_acceptance.py`](../../scripts/capture_final_acceptance.py); [`final_acceptance_manifest.json`](final_acceptance_manifest.json) records where it came from and the SHA-256 of every file, and `tests/unit/test_final_acceptance_evidence.py` checks the package against the committed configuration.

The earlier Stage 5C package (release v1, 215 chunks, pre-stage-2C CLI schema) is kept as history in [`../historical/`](../historical/stage5c_release_v1/README.md). Nothing in it describes the current product.

## What this evidence proves, and what it does not

| It proves | It does not prove |
|-----------|-------------------|
| The real pipeline (the `answer-claim` code path, release gate with full store recomputation, the production Chroma index, frozen retrieval and reranking, deterministic risk rules, customer-output policy, CLI serialization) behaves as specified for 14 recorded situations | The semantic quality of real query embeddings (see the retrieval summary) |
| The text a customer-facing draft may contain is decided by deterministic code, not by the model: a model draft that promises a refund, diagnoses, admits fault or leaks a prompt never reaches the draft in critical categories and is replaced elsewhere | The quality, tone or correctness of real model answers |
| The release gate accepts exactly this index and corpus (`index_integrity=store_recomputed`) | That the stored vectors were produced by the named embedding model (attested, not provable offline) |
| Retrieval results of the real evaluation run: metrics, pool reachability, no per-case regression against the previously accepted baseline, and what the deterministic layer does for each high/critical case | Generalisation beyond the 60 frozen cases, which also guided the choice of the retrieval configuration |

The scenario runs make **no OpenAI request and no network request** and need no credential: the query embedding is the stored vector of a named chunk of the production index (so retrieval returns that chunk's real neighbours) and the model reply is a fixed text or a raised error. Both stubs are visible in [`scenarios.md`](scenarios.md). The tool refuses to start with `OPENAI_API_KEY` in the environment and never reads the repository `.env`.

## The CLI contract these files show

`answer-claim` prints one JSON object per message. Fields (all present, keys sorted):

| Field | Meaning |
|-------|---------|
| `answer` | Exactly the text shown as the customer draft |
| `answer_provenance` | Why that text exists: `llm_draft` (the model draft passed the text policy), `category_template` (fixed text for a critical category, or for a case whose risk floor overrides a model out-of-scope verdict), `safety_replacement` (the model draft broke the text policy), `insufficient_context`, `failure_fallback`, `unsupported_language`, `out_of_scope` |
| `response_mode`, `generation_outcome` | Raw generation facts, for staff diagnostics; `answer_provenance` is the authority on the text |
| `failure_source` | `retrieval`, `context_build`, `generation` or `null` |
| `assessment_status` | `rule_match` (a deterministic rule matched), `no_signal` (supported language, no rule matched: the risk is **not determined**) or `unsupported_language` (not assessed; manual review) |
| `risk_floor` | The raw deterministic lower bound. Only an affirmative level when `assessment_status` is `rule_match`; `low` with `no_signal` is the neutral bound, not an assessment |
| `risk_label`, `risk_note` | Customer-facing/staff-facing wording of the same status |
| `handoff_required`, `priority_handoff`, `handoff_notice` | Handoff guidance derived from the floor |
| `citations` | Sources that support `answer`. Non-empty only for `llm_draft` |
| `retrieved_materials` | Retrieved fragments that do **not** support `answer`, listed for manual checking. Empty for `llm_draft` and `out_of_scope` |

## Provenance and identity

`final_acceptance_manifest.json` states:

- `source.git_commit` and `source.source_tree_clean`: the commit whose code produced the files (generated from a clean tree; later commits add only the evidence and documentation);
- `run_mode: deterministic_stub_run`, `external_requests` (`openai: 0`, `network: 0`), and the environment facts (no `OPENAI_API_KEY` in the process environment, repository `.env` not read, no tokenizer vocabulary needed);
- `release`: release id, canonical corpus id, `216` chunks / `10` documents, corpus fingerprint, chunk payload digest, model, dimension, index path, frozen config hash, `release_can_proceed`, `index_integrity`;
- `retrieval_evaluation`: the index fingerprint, evaluation dataset fingerprint, retrieval config hash and headline metrics of the retrieval run, and the SHA-256 of its raw artifact. That raw artifact (`data/05_evaluation/stage2g_pool_expansion.json`, about 3 MB) is a gitignored local output, like every generated evaluation file; `retrieval_summary.*` is what is derived from it and committed.

No absolute paths and no credentials appear in these files; a test enforces both.

## Regenerating

Needs the production index (`docs/07_index_provisioning.md`), a tree whose sources are committed, **no** `OPENAI_API_KEY` in the environment and, for the screenshots, `python -m pip install -e ".[screenshots]"` and a Chromium.

```powershell
python scripts/capture_final_acceptance.py --ui
```

The retrieval summary additionally needs the raw artifact of the evaluation run, which does need a key and spends embedding credit. Give the key in the process environment on purpose and name the outputs: the command's defaults are the tracked historical artifact `data/05_evaluation/vector_pool_expansion_v1.json`, which must not be overwritten.

```powershell
python -m customer_claims_rag.cli.evaluate_pool_expansion --index-dir data/04_index_production --output-json data/05_evaluation/stage2g_pool_expansion.json --output-markdown data/05_evaluation/stage2g_pool_expansion.md
```

On a machine with the production index and that artifact, `tests/unit/test_final_acceptance_evidence.py` also re-runs the scenarios and the derivation and fails if the committed files differ from what the code produces.
